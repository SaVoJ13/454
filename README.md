# salary — калькулятор зарплати (PWA)

Орієнтовний розрахунок зарплати brutto/netto для польського ринку праці (UA/PL інтерфейс, світла/темна тема, робота як встановлюваний застосунок).
Результат є прогнозом і не замінює розрахунковий лист роботодавця.

**Демо:** https://savoj13.github.io/salary/

## Режими

- **Гість** — усі дані зберігаються лише в `localStorage` на цьому пристрої.
- **PRO (після входу)** — синхронізація місяців і профілю в Firebase (Firestore), відпускні, поважна відсутність, лікарняний L4.
- **Офлайн** — якщо Firebase недоступний, застосунок стартує як гостьовий калькулятор, хмарні кнопки показують повідомлення.
  Залогінений користувач без мережі бачить локальну копію останніх 12 місяців (з позначкою дати копії). Збереження в хмару без мережі
  не виконується (повідомлення замість мовчазного зависання); дані на екрані не втрачаються, зберегти можна, коли мережа з'явиться.

## Структура

```

js/app.js           UI, профіль, хмара, події

js/firebase.js      ініціалізація Firebase
js/utils.js         formatPLN, showToast
js/monthcache.js    локальна копія місяців акаунта (офлайн)
js/stats.js         статистика за період (чисті функції)
js/charts.js        графіки «Статистика»: SVG без бібліотек
js/version.js       версія застосунку (єдине джерело)

tests/              математика (golden + еталон), i18n, кеш місяців, офлайн-старт, залогінений сценарій (фейковий Firebase), статистика й графіки,
                    оновлення, manifest, безпека, розкладка, версія

firebase.json, .firebaserc   деплой правил
```

## Запуск і тести

**Структура плоска:** усі тести лежать прямо в `tests/` (без вкладених підпапок), а JS — прямо в `js/`. Так файли легко завантажувати через мобільний GitHub:
«Upload files» кладе файл у ту папку, яку зараз відкрито, а підпапки створити важко. Не додавай вкладених папок.

Модулі ES не працюють з `file://`, потрібен локальний сервер:

```bash
npx serve .
npm test           # усі тести (Node 20+; у CI — Node 22)
npm run test:update   # лише якщо формули змінено свідомо
```

`tests/golden.json` фіксує результати `compute()` на наборі сценаріїв. Якщо `npm test` падає після рефакторингу, значить змінилися цифри. Без `golden.json` тест падає (тиха регенерація заборонена).

`tests/reference.mjs` порівнює `js/calc.js` з оригінальною математикою (вбудована в сам файл копія блоку `@@PURE` з `index.html` до розбиття на модулі) на десятках тисяч випадкових наборів. Це незалежний еталон: він не генерується з поточного коду. Не редагуй його без пояснення в коміті.

## Деплой (GitHub Pages)

Settings → Pages → Deploy from a branch → `main` / `(root)`.
**Після кожної зміни файлів підіймай `APP_VERSION` у `js/version.js`** (єдине джерело): вона показується в шапці поруч із «PRO», а `sw.js` бере з неї назву кешу. Без цього користувачі бачитимуть кешовану версію.

### Як користувач отримує оновлення

1. Браузер перевіряє `sw.js` і `version.js` в обхід HTTP-кешу (`updateViaCache: 'none'`), а встановлений PWA ще й щоразу, коли користувач повертається в застосунок.
2. Новий service worker прекешує файли в обхід HTTP-кешу, одразу перебирає керування і застосунок показує банер «Доступна нова версія» з кнопками «Оновити» / «Пізніше».
3. Після «Оновити» сторінка перезавантажується, і в шапці видно нову версію. Банера немає при першому встановленні.

### Іконки

`android-chrome-192x192.png` і `android-chrome-512x512.png` — звичайні (`any`), це основна графіка застосунку.
`maskable-192.png` і `maskable-512.png` — для адаптивних іконок Android: та сама графіка, зменшена до ~70% на суцільному темно-синьому тлі,
щоб усе важливе лишалось у безпечній зоні (коло ≈ 80%) і Android не обрізав напис та стрілку. Не підміняй їх копією `any`-іконок
(тест `tests/manifest.mjs` це відловить). Перевірити можна на https://maskable.app/editor.

У прекеш service worker входять лише manifest і малі (192) іконки; великі браузер завантажує сам під час встановлення PWA.

## Вкладка «Статистика»

Третя вкладка: підсумок за обраний період і два графіки (`js/stats.js` рахує, `js/charts.js` малює).

- **Період:** останні 3, 6 або 12 місяців (рахуючи поточний) або «Роки» — один чи кілька років одразу (кнопки з роками, де є дані).
  **Майбутніх місяців немає:** максимум — поточний місяць (для поточного року — січень…поточний).
- **Відсутні місяці:** якщо в періоді є місяці без збережених даних, з'являється випадаючий список «Бракує даних за місяців: N» з їхніми назвами. Майбутні місяці в ньому не показуються.
- **Кілька років:** стовпчик на рік (середнє на місяць) замість стовпчика на місяць; підпис показує, скільки місяців із даними.
- **Підсумок:** брутто й нетто за період, середнє нетто за місяць, місяць з найвищим нетто, скільки місяців із даними.
- **Дохід по місяцях:** пара стовпчиків брутто (сірий) і нетто (синій); дотик до місяця показує точні суми під графіком.
- **Структура змін:** кільце й легенда з відсотками (звичайні, нічні, надгодини, відпустка, L4, поважна відсутність) у змінах/днях.
- **Джерело даних:** гість — збережені місяці з `localStorage`; акаунт — місяці з хмари (без мережі — локальні копії).
  Для акаунта нетто місяця те саме, що в калькуляторі, зокрема з порогом PIT 120 000.
- **Чому SVG, а не Chart.js чи CSS-стовпчики з `style="height:…"`:** `style-src 'self'` блокує inline-стилі, а HTML-рядки через `innerHTML`
  заборонені тестом безпеки. Графіки будуються через DOM API (`createElementNS`) і стилізуються класами; нуль залежностей, ~7 КБ у прекеші.
  Єдиний «URL» у коді — ідентифікатор простору імен SVG, його ніхто не завантажує (дозволено в `tests/security.mjs` лише точним збігом).

## Поріг PIT 120 000 zł на рік

Для залогінених застосунок враховує другий поріг PIT (32% з надлишку понад 120 000 zł бази за рік) — `js/pit.js`.
`js/calc.js` не змінювався: він рахує PIT за 12%, а `pit.js` додає лише різницю, коли поріг перетнуто.

- Накопичена база береться з місяців цього року **перед поточним**, збережених у хмарі (без мережі — з локальних копій).
- Метод як у роботодавця: у місяць перетину 12% з частини під 120 000 і 32% з надлишку, далі 32%; щомісяця віднімається 300 zł (PIT-2).
  За рік виходить 10 800 zł + 32% надлишку, як за шкалою.
- База PIT місяця = брутто − ZUS − 300 (підвищені витрати: праця в іншій місцевості), рівно як у `calc.js`.
- Нижче порога результат такий самий, як раніше (перевіряє `tests/pit.mjs`).
- На сторінці «Деталі»: рядок «База PIT з початку року» і, коли є надлишок, «PIT 32% (понад 120 000)»; netto зменшується на цю суму.

**Обмеження:** гості поріг не бачать (немає збережених місяців); пропущені місяці року рахуються як 0 (є попередження «Збережено N з M»);
минулі місяці беруться з вашого введення, а не з реальних листків; L4 минулих місяців — за ставкою від окладу;
не моделюються ліміт ZUS, звільнення до 26 років понад 85 528 zł, кілька роботодавців.

## Скидання пароля

У формі входу є «Забули пароль?»: лист зі посиланням надсилає сам Firebase (`sendPasswordResetEmail`), пароль міняється на сторінці Firebase, не в застосунку.
Поведінка (перевіряє `tests/cloud.mjs`):

- email береться з поля «Email» (пробіли обрізаються); якщо порожньо, підказка без запиту;
- відповідь однакова, чи існує акаунт (не розкриваємо, які адреси зареєстровані);
- між листами пауза 60 с, щоб не засипати скриньку; після помилки пауза не вмикається;
- мова листа = мова інтерфейсу (`auth.languageCode`); без мережі показується повідомлення про недоступну хмару.

**Налаштування в консолі Firebase (один раз):**

1. Authentication → Templates → «Password reset»: обери мову (українська / польська) і за потреби відредагуй текст листа.
2. Authentication → Settings → «Email enumeration protection» — увімкни (тоді Firebase сам не розкриває, чи є акаунт).
3. Лист іде від `noreply@<проєкт>.firebaseapp.com` і інколи потрапляє у «Спам». Для надійнішої доставки в Templates можна підключити власний SMTP або домен відправника.
4. Посилання `continueUrl` навмисно не використовується: воно вимагало б додати домен у «Authorized domains». Після зміни пароля користувач просто повертається в застосунок і входить.

## Дані в Firebase

- `users/{uid}/months/{YYYY-MM}` — введені значення за місяць
- `users/{uid}/profile/userProfile` — профіль

## Безпека

- **Правила Firestore** лежать у `firestore.rules`: доступ лише власнику (`request.auth.uid == uid`), усе інше заборонено.
  Деплой: `npm i -g firebase-tools && firebase login && firebase deploy --only firestore:rules`
  (проєкт задано в `.firebaserc`). Перед деплоєм перевір правила в консолі Firebase → Firestore → Rules → Playground.
- **API-ключ** у `firebase.js` публічний за задумом Firebase. Обмеж його за доменом (HTTP referrers) у Google Cloud Console → Credentials: твій домен GitHub Pages і `localhost`.
- **CSP** задано через `<meta>` в `index.html` (GitHub Pages не дає ставити заголовки). Тому в розмітці немає inline-коду (`onchange=`, `style=`, `<script>` без `src`), це перевіряє `tests/security.mjs`.
  Якщо після змін вхід чи хмара не працюють, відкрий DevTools → Console, знайди «Refused to … Content Security Policy» і додай потрібне джерело в CSP. Вхід через popup/redirect (Google тощо) потребує додаткових дозволів (`frame-src` на `*.firebaseapp.com`, `script-src` на `apis.google.com`); для email/пароля вони не потрібні.
- **Firebase SDK** закріплено на версії 12.13.0 у `js/firebase.js` (однакова у всіх імпортах). Оновлюй усі три файли разом і перевіряй вхід та збереження місяця.
- **Вихід з акаунта** видаляє локальну копію профілю (`user_profile_<uid>`); гостьові дані лишаються.
- Тести безпеки: `npm test` (CSP, відсутність inline-коду, правила, версія SDK, `permissions` у CI). Вони статичні й не замінюють перевірку в браузері.
